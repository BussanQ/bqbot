# 阶段 4：工具与自动化

阶段 4 的核心实现已落地，2026-10-30 已补做本地定向回归及真实 WebView 设置入口操作。供应商账号、系统钥匙串与外部引擎端到端验收仍有环境依赖，详见文末。

## 桌面入口

打开「引擎设置」中的「工具与自动化」，可以管理 MCP 服务器、Composio 应用连接以及日程与 Webhook。自动任务列表提供编辑、手动运行、历史和删除入口。

桌面表单通过 `Desktop.Tools` 的显式命令调用本地服务，不向页面暴露服务 bearer token，也不提供通用 HTTP 代理。前端在 `web/tools.js`，Go 桥接在 `webgo/tools.go`。

## 自定义 MCP 服务器

支持三种连接方式：

| 方式 | 配置 | 行为 |
|---|---|---|
| `stdio` | 可执行命令、参数、环境变量映射 | 每轮启动本地 MCP 子进程，通过标准输入输出通信 |
| `http` | HTTP(S) 地址、请求头映射 | 使用 Streamable HTTP，可接收 JSON 或 SSE 响应 |
| `sse` | HTTP(S) 地址、请求头映射 | 使用旧式 SSE 连接，消息端点必须与服务器同源 |

每项配置可启用或暂停，并限定可使用它的 Bot；不选择 Bot 表示全部。配置变更用于后续轮次。每轮建立连接、发现工具，将工具加入 bqbot MCP 服务，并在轮次结束或取消时清理连接与子进程。

环境变量和请求头映射的值都是**环境变量名**，不是凭据本身。例如：

```json
{
  "env": { "API_KEY": "MY_MCP_API_KEY" },
  "headers": { "Authorization": "MY_MCP_AUTHORIZATION" }
}
```

上例展示两类映射的格式：`stdio` 使用 `env`，远程连接使用 `headers`，不能混用。Go 服务从自己的进程环境读取值；`Authorization` 的环境变量值需包含完整的 `Bearer …` 等认证格式。配置中缺少对应环境变量时，该轮会明确报错。远程地址不接受 URL 用户信息、查询参数或 fragment，客户端不跟随重定向。

外部工具调用经过现有审批机制：Ask 模式需确认，自动编辑模式不会自动批准任意 MCP 工具，完全自动模式遵循其自动批准规则。consult 轮次不连接外部 MCP。工具发现发生在工具调用审批之前；启用的 stdio 服务器会在准备轮次时启动。

当前 OpenAI 兼容 API 驱动没有 MCP 工具能力；为其启用适用的外部 MCP 配置时，轮次会明确报错。外部引擎的实际接入情况仍需端到端验收。

## Composio 应用连接

1. 在 Composio 设置中保存 API 密钥。Go 通过 `mygo.Secrets.Service("bqbot")` 写入系统凭据存储，键名为 `composio-api-key`；读取状态只返回 `configured` 标记，不回传密钥。
2. 填写用户 ID、授权配置 ID、MCP 地址和 Bot 作用域，先保存配置。启用工具需要用户 ID 与 MCP 地址；发起授权还需要授权配置 ID。
3. 点击「授权应用」，服务请求 Composio v3 的连接链接，桌面打开返回的 HTTPS 授权页面。完成后可用「查看连接」读取应用及连接状态。
4. 启用配置后，适用 Bot 的后续轮次通过 Composio MCP 使用工具，调用沿用 bqbot 审批。

MCP 地址必须是 `https://mcp.composio.dev` 下的地址，不接受 URL 凭据、查询参数或 fragment。API 密钥仅在 Go 发起请求时读取，通过 `x-api-key` 请求头传递；服务不跟随重定向，不向界面回传提供商错误响应正文。

移除密钥会删除本机保存的凭据；不会调用 Composio 撤销已有应用授权。真实授权流程和系统钥匙串读写尚未实测。

## 多 Bot 协调

保留 `ask_bot(name, question, thread?)` 作为单目标入口。新增 `coordinate_bots`，一次派发 1–4 个任务，目标使用 Bot ID 或唯一名称；同一批次不能重复目标。例如：

```json
{
  "assignments": [
    {
      "bot": "研究员",
      "task": "阅读现有方案并列出待澄清的问题",
      "mode": "consult",
      "reply": "report",
      "done_when": "给出问题列表及对应依据"
    }
  ]
}
```

工具立即返回受理回执，包括 `assignment_id`、目标线程和消息 ID。发起者应结束当前轮次，目标完成后由服务在原会话自动唤醒续答；多层结果逐层返回。目标正忙时，任务与普通消息共用 FIFO。

| 参数 | 含义 |
|---|---|
| `mode: "delegate"` | 默认委派模式，继承转交链的审批模式 |
| `mode: "consult"` | 咨询模式；审批层仅允许明确的读取工具，拒绝其他工具请求，禁用外部 MCP 和关闭线程操作 |
| `reply: "report"` | 默认返回结果并唤醒发起者 |
| `reply: "none"` | 派发任务但不唤醒发起者，仍记录任务状态 |
| `mode: "rework"` | 配合 `assignment_id` 对已完成或失败的可见任务返工，复用原目标线程 |
| `done_when` | 作为验收条件附加给目标，要求其说明是否满足；不自动执行测试或判定完成质量 |
| `thread: "new"` | 私人委派创建新线程；频道委派和返工不接受该参数 |

转交深度最多 4 层，不能派给自己或链上的祖先。每轮最多派发 8 个任务，同一协调链最多 32 个，自动续答仍受这些限制。频道任务只能派给当前频道成员，并留在本频道。consult 限制沿链传递，原咨询任务返工时也保留该限制。consult 的当前实现依赖引擎将受控操作交给审批层；各真实 CLI 的原生工具权限边界尚未完成验收。

`assignment_status` 不带参数时返回当前会话可见的任务；传入 `assignment_id` 时查询单项。可见范围由发起者、目标和根任务的 Bot、线程及频道共同限制。任务记录包含进度、结果、错误、父任务和返工关系。

停止、关闭或删除相关会话会取消关联任务。服务重启后，原 `queued`、`running`、`waiting` 任务标记为 `interrupted`，不自动重放可能产生副作用的工作。

## 日程与运行历史

自动任务指定执行 Bot 和任务指令，在该 Bot 主对话中排队，使用普通聊天的引擎和审批模式。服务运行期间每秒检查一次日程；应用或 `bqbot serve` 退出后不会继续调度。

| 类型 | 设置 | 调度规则 |
|---|---|---|
| `once` | 一次性时间 `at` | API 使用 RFC3339；桌面使用本地日期时间输入，到期触发后自动停用 |
| `weekdays` | `time` 和 `timezone` | 指定时区内周一至周五，时间格式 `HH:MM`；不计算法定节假日或调休 |
| `interval` | `interval_seconds` | 1 秒至 365 天；从本次调度时间计算下一次，不逐次补跑错过的间隔 |
| `webhook` | 启用任务和接收器 | 由鉴权的本机 HTTP 请求触发 |

同一任务上次运行仍在排队、执行或等待关联协调链结束时，再次触发记为 `skipped`。不同任务仍按 Bot 的正常队列执行。「运行」按钮可以手动运行暂停的任务，不推进其日程。暂停阻止后续自动触发；删除任务会取消该任务的活动工作，并保留运行历史。

历史记录包括来源、开始与结束时间、状态、结果或错误，状态有 `running`、`completed`、`failed`、`canceled`、`skipped`、`interrupted`。重启将遗留的 `running` 标记为 `interrupted`；已保存的日程继续调度，到期任务在下一次检查时处理。历史以 500 条为裁剪阈值，优先保留运行中的记录。

## Webhook 接收器

在「日程与 Webhook → Webhook 接收器」中先生成密钥，再开启接收器。默认只监听 `127.0.0.1:8800`，与主服务使用不同的 bearer 密钥。新密钥仅在生成或轮换时返回，状态查询不返回密钥；轮换后旧密钥立即失效。接收器的启用状态会持久化，服务启动时尝试恢复监听；端口占用等错误会显示在状态中。

接收器仅开放以下路由，二者均要求 `Authorization: Bearer <密钥>`：

| 方法与路径 | 行为 |
|---|---|
| `GET /health` | 返回接收器健康状态 |
| `POST /hooks/{routine_id}` | 触发已启用且类型为 `webhook` 的任务 |

POST 请求体是 JSON 对象，例如 `{}` 或 `{"text":"本次事件的补充信息"}`。`text` 追加到任务指令后，整体请求体上限为 64 KiB；未知字段和多个 JSON 值会被拒绝。成功受理返回 HTTP 202 和运行记录，重叠触发也可能返回 `skipped`，不能将 202 当成任务已完成。

接收器校验 Host，并拒绝携带 Origin 的请求，供本机程序调用。此端口不开放主服务的 Bot、审批或配置接口。

## 服务接口与持久化

以下管理接口位于主服务，沿用其鉴权；Webhook 的 8800 端口不提供这些接口。

| 接口 | 用途 |
|---|---|
| `GET / PUT /v1/mcp-servers`；`DELETE /v1/mcp-servers/{id}` | MCP 配置管理 |
| `GET / PUT /v1/composio` | Composio 非秘密配置及配置状态 |
| `PUT / DELETE /v1/composio/key` | 写入或移除系统凭据存储中的密钥 |
| `POST /v1/composio/connect`；`GET /v1/composio/accounts` | 获取授权链接和应用连接状态 |
| `GET / PUT /v1/routines`；`DELETE /v1/routines/{id}` | 自动任务管理 |
| `POST /v1/routines/{id}/run`；`GET /v1/routines/{id}/history` | 手动运行及历史 |
| `GET /v1/webhook`；`POST /v1/webhook/enable`、`disable`、`rotate` | 接收器状态、启停和密钥轮换 |

数据保存在 `BQBOT_HOME` 指定目录，默认 `~/.bqbot`，JSON 文件通过现有存储层以 `0600` 权限写入：

| 文件 | 内容 |
|---|---|
| `mcp.json` | MCP 启动和连接配置，环境变量与请求头只保存变量名 |
| `composio.json` | Composio 非秘密配置；API 密钥保存在系统凭据存储 |
| `assignments.json` | 协调任务的进度、结果及关系 |
| `automation.json` | 日程和运行历史，触发记录与日程推进一起保存 |
| `webhook.json` | 接收器启用状态和独立密钥，不通过状态接口回传 |
